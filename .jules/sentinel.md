## 2024-05-14 - Host Header Injection via Unvalidated Forwarded Host
**Vulnerability:** The API server's clerk proxy middleware manually parsed the `x-forwarded-host` and `x-forwarded-proto` headers to build proxy URLs, while the frontend standalone server blindly trusted these headers to build absolute paths for templates. Because these headers are client-controlled, an attacker could spoof the protocol or host, causing the server to proxy requests to an attacker-controlled server (potentially leaking secrets like `Clerk-Secret-Key`), or inject malicious payloads into template URLs (SSRF/Host Header Injection/XSS).
**Learning:** Directly reading forwarded headers like `x-forwarded-host` or `x-forwarded-proto` bypasses the framework's proxy trust mechanisms. If `x-forwarded-host` contains comma-separated values, blindly passing it to URL parsers can crash the server or be exploited. The primary `Host` header must also be validated to prevent Host Header Injection if no proxy headers are present.
**Prevention:** In Express, always rely on `req.protocol` and `req.hostname`, which securely evaluate the headers according to the `app.set("trust proxy")` configuration. In plain Node.js servers without these frameworks, the `host` and `x-forwarded-host` headers must be explicitly validated and sanitized (e.g., using the `URL` parser to extract just the valid `.host` portion) before using them to construct absolute URLs.
