## 2024-05-14 - IP Spoofing via Unvalidated Header
**Vulnerability:** The API server's clerk proxy middleware manually parsed the `x-forwarded-for` header from incoming requests to determine the client IP address. Because this header is client-controlled, a malicious actor could send a spoofed `x-forwarded-for` header to bypass IP-based logging, rate limiting, or to mask their true origin in the proxy request.
**Learning:** Manually parsing `x-forwarded-for` directly from `req.headers` skips the framework's secure handling of proxy trust. When an Express application is running behind a trusted proxy (like a load balancer or ingress controller), the framework needs to be explicitly configured using `app.set("trust proxy", ...)` to securely parse the XFF header, starting from the most trusted proxy backwards.
**Prevention:** Always use `req.ip` in Express (or the equivalent secure accessor in other frameworks) rather than reading `req.headers["x-forwarded-for"]` directly. Ensure the application's `trust proxy` setting is correctly configured for the deployment environment so that `req.ip` returns the true client IP instead of a spoofed or intermediate proxy IP.

## 2025-02-14 - Protocol Spoofing and Host Header Injection
**Vulnerability:** The API server's clerk proxy middleware manually parsed the `x-forwarded-proto` and `host` headers from incoming requests to construct the proxy URL. Because these headers are client-controlled, a malicious actor could send a spoofed `x-forwarded-proto` or `x-forwarded-host` header to manipulate the protocol or host, leading to protocol spoofing, Host Header Injection, or Server-Side Request Forgery (SSRF) vulnerabilities.
**Learning:** Manually parsing `x-forwarded-proto` directly from `req.headers` skips the framework's secure handling of proxy trust. When an Express application is running behind a trusted proxy, the framework needs to be explicitly configured using `app.set("trust proxy", ...)` to securely parse these headers. Node.js also joins duplicate headers into comma-separated strings, which must be handled.
**Prevention:** Always use `req.protocol` in Express to respect proxy trust rules and validate the extracted protocol. When extracting the host, safely parse `x-forwarded-host` by extracting and trimming the first value to handle comma-separated strings safely.

## 2025-02-14 - Host Header Injection via Unvalidated X-Forwarded-Host
**Vulnerability:** The API server's clerk proxy middleware attempted to mitigate Host Header injection by manually prioritizing and parsing the `x-forwarded-host` header. However, reverse proxies often pass `x-forwarded-host` through untouched unless explicitly configured, meaning unconditionally trusting it introduces a worse Host Header Injection vector.
**Learning:** Never manually parse proxy headers (like `x-forwarded-host` or `x-forwarded-proto`) directly from `req.headers`. These headers must be processed securely by the framework's `trust proxy` mechanism to ensure they actually originated from a trusted downstream proxy.
**Prevention:** Always use secure framework accessors (like `req.hostname` and `req.protocol` in Express) which respect `trust proxy` settings. Since `req.hostname` strips the port, if preserving the port is necessary for local proxies, extract the port from the raw `host` header and append it to the securely validated `req.hostname`.
