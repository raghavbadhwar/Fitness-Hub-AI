## 2024-05-14 - IP Spoofing via Unvalidated Header

**Vulnerability:** The API server's clerk proxy middleware manually parsed the `x-forwarded-for` header from incoming requests to determine the client IP address. Because this header is client-controlled, a malicious actor could send a spoofed `x-forwarded-for` header to bypass IP-based logging, rate limiting, or to mask their true origin in the proxy request.
**Learning:** Manually parsing `x-forwarded-for` directly from `req.headers` skips the framework's secure handling of proxy trust. When an Express application is running behind a trusted proxy (like a load balancer or ingress controller), the framework needs to be explicitly configured using `app.set("trust proxy", ...)` to securely parse the XFF header, starting from the most trusted proxy backwards.
**Prevention:** Always use `req.ip` in Express (or the equivalent secure accessor in other frameworks) rather than reading `req.headers["x-forwarded-for"]` directly. Ensure the application's `trust proxy` setting is correctly configured for the deployment environment so that `req.ip` returns the true client IP instead of a spoofed or intermediate proxy IP.

## 2024-05-14 - Denial of Service and SSRF via Unvalidated Headers in Raw Node Servers

**Vulnerability:** A static HTTP server implemented using Node's raw `http` module was vulnerable to Denial of Service (DoS) and Server-Side Request Forgery (SSRF)/Host Header Injection. The DoS occurred because `new URL(req.url, 'http://' + req.headers.host)` was not wrapped in a `try...catch` block. If an attacker provided a malformed `Host` header (e.g., `%foo`), `new URL` threw a `TypeError: Invalid URL` which crashed the Node process. Additionally, the server blindly trusted the `x-forwarded-host` header to generate absolute URLs, allowing Host Header Injection/SSRF since raw Node servers lack the proxy trust mechanisms found in frameworks like Express.
**Learning:** Constructing a `new URL()` using client-controlled headers like `req.headers.host` can crash the server if the input is malformed, even if a fallback is provided. Furthermore, raw Node.js servers should not manually parse proxy headers like `x-forwarded-host` because they have no way to verify if the header came from a trusted proxy or directly from a malicious client. When parsing proxy headers like `x-forwarded-proto` (which may be necessary if deploying behind an SSL-terminating load balancer), one must account for comma-separated lists from chained proxies.
**Prevention:** Always wrap `new URL()` parsing in a `try-catch` block to handle invalid inputs safely and prevent uncaught exception crashes. Avoid parsing `x-forwarded-host` in raw Node servers; use the standard `Host` header instead. When parsing headers like `x-forwarded-proto`, split the string by commas and extract the first trimmed value.
